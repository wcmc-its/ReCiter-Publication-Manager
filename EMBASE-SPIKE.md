**Every heading the model emitted was real. The control returned 0.** That control is the load-bearing
measurement: it proves Ovid does **not** silently fall back to a keyword search when a heading does not
exist. So a hallucinated heading can only ever cost **sensitivity** (its line contributes nothing, and
the free-text line beside it still carries the concept) — it can **never produce a wrong number**. And
`probiotics/` → 77,017 shows Ovid resolves a near-miss synonym to the preferred term on its own.

**The one hazard that survives:** a dead heading is invisible to *us*, because we cannot count Ovid. The
librarian standing in front of Ovid can see it in seconds — so the export now tells them to run each
Emtree line on its own, and that a line returning 0 is a dead line.

## READ THIS FIRST: the platform is OVID, not Embase.com

The first version of this spike was in the wrong dialect and Ovid rejected it outright —
**`Invalid subheading: exp`**. That error is the finding, and it is worth more than the spike it
interrupted.

**WCM does not have Embase.com. WCM has Embase through OvidSP**
(`ovidsp-dc2-ovid-com.ezproxy.med.cornell.edu` → *Embase 1974 to 2026*). Ovid and Elsevier are
**different platforms with different query languages over the same Emtree thesaurus**:

| | Elsevier (Embase.com) | **Ovid (what we actually have)** |
|---|---|---|
| Explode a heading | `'probiotic agent'/exp` | **`exp probiotic agent/`** |
| Heading, no explode | `'probiotic agent'/de` | **`probiotic agent/`** |
| Free text | `probiotic*:ti,ab,kw` | **`probiotic*.ti,ab,kw.`** (trailing period is required) |
| Phrase | `'gut microbiome':ti,ab,kw` | no quotes; use adjacency: `(gut adj3 microbiome).ti,ab.` |
| Combine history lines | `#1 OR #2` | **`1 or 2`** (bare number, lowercase operator) |

**The consequence for the app, and it is the useful one: a dialect is PLATFORM + DATABASE, not
database.** The `DIALECTS` table currently keys on the database. The Emtree *vocabulary* is the same
either way — only the *query language* differs — so if WCM ever moved Embase to Elsevier, the concept
labels and the headings survive and only the rendering changes. That is precisely the
Concept/Rendering split working as designed, and it is an argument for the split, not against it.

Everything below is now **Ovid syntax**, regenerated by `us.anthropic.claude-opus-4-8` — the same model
and the same prompt shape the app already uses for PubMed and Scopus. Question: **Do probiotics reduce
symptoms of depression in adults?**

### Why this audit exists at all

An Emtree heading that does not exist **retrieves 0 records without necessarily raising an error**. It
quietly contributes nothing to its block, so the controlled-vocabulary arm of that concept is dead, the
block runs on free text alone, and the strategy still looks perfectly plausible on the page. For PubMed
we can count a MeSH line and see that it is non-zero. **For Embase we have no API, so the app can never
check this for you.** A human has to, once, now.

**And the model is not stable about which headings it emits.** Across three runs it has variously
emitted, and then dropped, `'probiotics'`, `'depressive symptom'`, `Lactobacillus` and `Bifidobacterium`
as headings — sometimes promoting them to headings, sometimes demoting them to free text. So *"it worked
when I tried it"* is not evidence, and that instability may turn out to be the real finding.

## The decision this feeds

**The headings resolve** → **build it.** `Db` gains `'embase'` (rendered for **Ovid**); `DIALECTS` gains
an entry — exactly what that table exists for, and the platform-vs-database distinction above is now part
of what a dialect *is*. `runStrategy` gets one `countable: false` branch (`countIn(db)` at
`literatureSearch.controller.ts:187` is the single count dispatch, and therefore the seam). Every row
renders an **em-dash**, never a zero. The export **declares** it: *"Embase (Ovid) strategy — drafted, not
executed. Run it in Ovid; we have no API access to count it."* Cochrane requires an Embase search, and
this is what takes Mode 1 from useful to compliant.

**Some resolve to 0** → we have found the failure mode. Fixable, but not free: either the prompt leans
harder on free text whenever it is not certain of a heading (it is *already* told to do that — and it
still wobbles run to run), or we accept that the controlled-vocabulary arm is unverifiable and ship
**free-text-only** Ovid lines. That is honest, still Cochrane-shaped, and loses some sensitivity — which
a librarian should be the one to accept or refuse.

**Most resolve to 0, or line 7 is nonsense** → **axe the card.** Delete the disabled checkbox
(`LiteratureSearch.tsx:161`) and the "Coming soon" note (near :1589), and say in the methods that Embase
was not searched.

**Whatever the answer, the disabled "Coming soon" card does not survive this.** Leaving it is the one
outcome that is definitely wrong: it is a promise the repo cannot currently keep.

## Reference — what is already settled, so nobody re-litigates it

- **The entitlement blocks COUNTING, not WRITING.** We have no Embase **API** on either platform. But a
  *strategy* is text a librarian pastes into Ovid, **which WCM has**. That is why strategy-only is
  buildable today with no entitlement at all — and why it can never show a count.
- **A dialect is PLATFORM + DATABASE.** Ovid and Elsevier speak different languages over the same Emtree.
  This is new, it came out of this spike, and it belongs in the dialect table's definition.
- **There is no MeSH→Emtree translation layer, ever.** The model writes native Ovid/Emtree **from the
  question**, sharing only the concept *labels* with the PubMed strategy. Cochrane and PRESS expect a
  bespoke, separately peer-reviewed strategy per database; a mechanical transliteration is exactly the
  artifact a librarian rejects at review.
- **EMBASE EMBEDS MEDLINE.** Its counts overlap PubMed's massively and must **never** be summed. (Moot
  for strategy-only, which produces no counts — but it is why "just add the two numbers" is never the
  next step.)
